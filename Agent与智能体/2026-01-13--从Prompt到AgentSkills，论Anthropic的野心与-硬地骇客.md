# Agent Skills 是工程进化还是概念包装？硬地骇客解剖 Anthropic 的三层抽象

平台：小宇宙｜时长约 54 分钟

## 知识概览

这期硬地骇客聊的，是 Anthropic 在 MCP 之后又抛出的新标准 Agent Skills。主播们自嘲 MCP 还没消化完，各家编程工具已经默认跟进，仿佛 Anthropic 一开口，大家就默认这是正确方向。整期围绕一个问题展开：它到底是一次实打实的工程进化，还是行业集体接受的一次概念迁移。答案没有一边倒，但拆得很细，从抽象层、运行时一路聊到开源生态和模型厂商的野心。

节目最有价值的部分，是把三个常年混着说的概念摆到了三个层次上。Function Calling 在最底层，只是给模型一双调用外部 API 的手；MCP 在中间，是把外部 API 摆上货架、让模型能发现的标准协议；Agent Skills 在最上面，主体是纯业务流程知识的文档手册，告诉模型一件事先干什么再干什么。而 skill 运行中仍要借助下面两层去真的拿到数据和执行动作，它内部甚至还能内嵌 MCP 和脚本，这才构成完整定义。

主播们以自家播客总结产品为例，聊了一线工程取舍：技能包到底该拆多细、确定性流程要不要换成 agent、排障运维这类高不确定性场景为什么反而适合做成 skill，以及一个贯穿全场的判断，agent 效果的天花板根本不在 skill 写法，而在底座模型。期间也讲了 Docker 式的标准之争、中国团队为什么不太会定义标准，还抛出一个相当阴谋论的收尾话题：skills 会不会是大模型厂商收割社区知识的开源阳谋。

一句话总结这期的落点：skills 解决的是怎么把一个问题描述清楚、怎么让业务知识可复用，它不保证效果，保证效果仍然靠模型能力和持续调优。但对所有做 AI 应用的人，把手工反复做的事工具化、把业务知识组件化，已是绕不开的工程方向。

**适合谁听：**
- 用 Claude Code、各类 coding agent 或自建 agent 的开发者，能拿到 skills 该拆多大、description 怎么写才不踩坑的实操判据
- 做 AI 应用或 AI 内容产品（尤其播客、笔记、写作类）的创业者，能听到 workflow 与 agent 按确定性和成本取舍的真实决策
- 被 MCP、Function Calling、Agent Skills 几个概念绕晕的普通用户，能一次理顺三者关系
- 关心大模型厂商生态与开源策略的人，能听到关于开源阳谋和 skill marketplace 的完整推演
- **可以跳过**：对产品内部功能怎么切 skill 的具体推演不感兴趣的话，前两段概念梳理和最后一段生态讨论已经足够

## 重要观点

**1. Function Calling、MCP、Agent Skills 是三个层次，不是三个别名**
三者的关系用一句话说，是递进与包含：工具调用在最底层，只负责让模型能调用外部 API；MCP 是中间的标准协议，把一套外部 API 暴露给模型去发现；Agent Skills 在最上层，主体是纯业务流程与知识的 markdown，描述一个完整任务该按什么标准、什么顺序完成。skill 在跑的时候仍然要通过 MCP 去发现 API，再靠工具调用去真的执行。主播还补了一个容易踩的误区：不是所有 MCP 都是 skill，MCP 只是 skill 的可选组成部分，skill 的本体其实是把过去那些很灵的 prompt 结构化之后再加规范，再可选挂上 MCP 和脚本。
小白视角解读：可以把三层想象成员工、通讯录和老板给的手册。工具调用是让 AI 能伸手干活，MCP 是告诉它电话本上有哪些号码可以打，Agent Skills 是老板亲手写的完整工作流程。普通人别再问这三个谁替代谁，它们本来就是层层叠加的，你写 agent 时想清楚自己改的是哪一层就行。

**2. Agent Skills 表面是一堆 markdown，底下躺着一个完整的运行时**
文档界面背后，其实是 Claude Agent SDK 这个等价于 LangChain、LangGraph 的框架层，推理、规划、执行、对 MCP 与工具调用的管理都在那一层做完。Anthropic 先做了给开发者的框架，再往前走一步，把同一种能力包装成文档驱动的用户界面给非开发者用，门槛一下子低了很多。所以看到只是一堆 md 文件就开嘲讽的工程师，恰恰没看见人家把复杂封装藏在了哪。
小白视角解读：就像点外卖只用看 App 菜单，不用知道后厨怎么炒。文档是 Anthropic 故意留给用户的简单入口，底下的引擎早搭好了。普通人能带走的是：评估一个 AI 方案时别只看露出来的那层界面，要看它背后有没有真正扛得住的运行时。

**3. skill 的 description 是命根子，写不清就触发不了**
frontmatter 里的 description 是 Agent SDK 做自动发现与动态加载的开关：用户一句自然语言进来，靠它判断该调哪个 skill。官方 troubleshooting 里最常见的两个问题，skill 没被触发和多个 skill 冲突，根源几乎都是 description 写不清楚、区分度不够。除了 description，skill 文件夹还能带子文档和脚本做渐进式加载，用到才读，从而缓解上下文长度压力，减少模型执行多轮后忘事导致的低质量产出。
小白视角解读：description 就像公众号的简介和标题，决定平台把你的内容推给对的人。与其说这是写作技巧，不如说这是给 skill 做检索优化。普通人写任何给 AI 用的配置，都要把什么场景用我这件事写到最清楚，命中率先于内容细节。

**4. 一个 skill 的最佳粒度，是一句话能触发，但得培训新人一下午**
Anthropic 自己的 PPT、Word、PDF 这几个官方 skill 都是这个力度：你能一句话说清这个活是什么，但真要让一个新人干出符合标准的产出，得教他一下午。掌握了之后只需一句话他就能执行，这就是一个被内化的技能。反过来，太细的 skill 会变成碎片，太粗的又回到一个大而全的 prompt。主播判断，对他们这种业务，整个逐字稿结构化可以是一个 skill，翻译可以是一个 skill，不必拆成一个个单节点。
小白视角解读：拆多细有个很土的测法，想象你要把这件事外包给一个从没干过的新人。一句话说不清是什么的，太大；不用教就会的，太小；教一下午能会、会了之后一句话就能指挥的，刚刚好。普通人给自己的 AI 工作流搭技能包时，就用这个测法切边界。

**5. 排障运维这种想不出会出什么事的活，比确定性流程更适合 agent**
主播设想把查数据库原数据、翻日志、查代码分别封装成工具，再把整个排查流程写成 skill，出了错丢给它，让它按流程自己把三个地方查一遍再给出解释，能极大解放人的重复劳动。但反过来，播客总结这类确定性主流程要死守 workflow：完全可控、成本可算。agent 一旦无人值守就会陷入规划、执行、失败、再规划的大循环，token 哗哗烧，结果还不一定对。
小白视角解读：判断一个活该交给 workflow 还是 agent，就看它的意外率。流程固定、出错可预期的走 workflow，稳且省；什么幺蛾子都可能出的，才值得让 AI 自己摸索。普通人别一上来就把什么都做成 agent，先分清你手里哪些是规则活，哪些是探索活。

**6. agent 智能的上限在模型，skill 只是把模型能力放大的开关**
主播直言，同样的 agent 配置，用 Gemini 2.0 驱动会感觉驱动不动，换到 3 Pro 就很顺；在 coding 场景里 Claude 和 MiniMax、智谱系模型的产出差距是巨大的。最近各家模型（K2、DeepSeek V3.2）的优化重心也都在 agent 的规划推理执行链路上。所以 workflow 的上限写死在人给的规则里，agent 的上限随模型版本抬升，这才是大家越来越敢用 agent 的根本原因。
小白视角解读：别把功劳都记在我会写 prompt、我会调 skill 上，底座模型才是天花板，skill 只是把天花板显形。普通人如果同样的工具链效果天差地别，先怀疑是不是模型档次差了一截，再回头改自己的配置，顺序别反。

**7. skills 把领域知识从 agent 里抽出来，让 agent 变轻、知识变可插拔**
以前的 agent 很重：除了领域知识，还背着对不同 MCP 或硬编码 API 的对接、环境权限、memory 结构一堆东西，想改一点业务逻辑就牵一发动全身，不好改也不好复用。skills 把领域业务知识单独抽成一个方便修改复用的能力包，agent 退化成 runtime，具体怎么干活交给 skill 这个工作手册。主播们据此判断，行业不需要再堆一大堆新 agent，少量核心 agent 挂上不同 skill 就能覆盖需求。
小白视角解读：以前每个 agent 都是人格加知识加一堆接线的缝合怪，现在人格和接线留在 agent 里，知识变成可插拔的插件，换知识不用换 agent。普通人可以把自己重复做的工作流一个个沉淀成这种插件，用的时候一句自然语言就能召唤。

## 信息差

**1. 被吐槽的一堆 markdown，恰恰是 Anthropic 故意的**
很多工程师看到 Agent Skills 的第一反应是，这不就是 markdown 吗，搞这么多概念干嘛。但主播点破，让普通用户只接触一堆文档，正是 Anthropic 的设计意图：它把用户接口定义为文档驱动，复杂的框架层藏在下边。人们以为的简陋，其实是产品化之后刻意留下的低门槛入口。
小白视角解读：大多数人评判技术深浅喜欢看表面复杂度，但真正好的抽象是让使用者只看到简单。别再用这不就是 X 来否定一个方案，先问一句，它把复杂藏到哪去了，藏得够不够深。

**2. 一个 MCP 也能干完整件事，但和 skill 是两回事**
同样是从播客音频做到结构化总结，你可以写一个 MCP 全包，但那是把活外包给了 API 背后某个你看不到的模型，它内部可能也藏着一个 skill，是黑盒。而写 skill 是让你自己的模型按你的手册执行，每一步透明可见。能做同一件事不代表是同一个东西，差别在于控制权在哪里。
小白视角解读：大多数人以为能实现同样功能就等于同样架构，其实外包和自营都能把事办了，但可控性完全不同。普通人挑 AI 方案时要追问一句：这活是在哪跑的，我能不能看到过程，能不能改规则。

**3. skills 出来不等于 workflow 过时，define、扣子声量变小另有原因**
观察者发现 define、扣子这类 workflow 平台声量变小了，容易归因于 skills 的冲击。主播们却认为，根因是大模型变强让 agent 这种高上限形态变得可用了，而不是 skills 替代了 workflow。skill 本身不解决确定性问题，skill 一多，调用命中率照样会下降，老问题还在。显式点名或斜杠调用能提高命中率，但仍做不到 workflow 那种逐步精准执行。
小白视角解读：人们总爱把两个同时发生的事说成因果关系。技能包流行和工作流平台降温是并行趋势，前者靠的是底层模型进步，不是谁把谁干掉了。普通人选型别追新词，确定性任务该用工作流还用工作流。

**4. Anthropic 式成功不在技术，而在把技术定义成标准的产品能力**
主播用 Docker 做对照：早年阿里做容器化已经深入生产环境，镜像也不是没做过，只是用土办法自己写，没人想到把它抽象成一个可发布、全世界都能用的标准。能提出 MCP、skills 并让全行业默认跟进的团队，是真正会做产品的人。反观不少中国团队，技术做得很牛，却不擅长命名、不擅长把技术再往上封装半步变成出圈的概念。
小白视角解读：大多数人把技术强等同于产品强，其实中间隔着会不会把它包装成标准让人接受这一层。普通开发者别只顾埋头实现，偶尔抬头想想，你做的东西能不能再往上抽象一层，变成一个别人愿意直接调用的接口。

**5. skills 可能是大模型厂商的开源阳谋，也可能是 skill 版的 app store**
主播的阴谋论推演：skills 用 MIT 协议开源，社区贡献各行各业的专业知识，模型厂筛一筛就能内化进下一代产品，就像 ChatGPT 能做健康版、OpenAI 花一亿美金收购一个只干了六个月、产品还没上线的四人健康团队。另一派则反驳：skill 装的是会持续迭代、因人而异的业务知识，不像常识可以被大模型吸收，它更像操作系统上可以随时替换的 app，会走 marketplace 生态，模型厂更可能收购做得好的 skill 产品而不是把它学走。两种可能都被认真聊了一遍。
小白视角解读：普通人以为开源等于白嫖安全，其实开源从来是各方博弈的场子。你在公开贡献专业知识时，至少该知道它有被吸收的可能；反过来，如果你的技能包在别人的生态里跑得很好，也可能成为被收购的资产而不是被吃掉的养料。多留一个心眼，别天真也别全阴谋论。

## 章节纪要

**开场：抛出本期问题**
- 主播开场指出，Anthropic 在编程领域是王者，Claude Code 已成行业标杆，但它还擅长另一件事，把怎么用模型的方法论推成行业共识。
- MCP 大家还没消化完，Agent Skills 又来了，各家编程工具已默认跟进，仿佛 Anthropic 开口即标准。
- 本期核心问题：Agent Skills 到底是一次工程进化，还是一次集体接受的概念迁移。

**从抽象层到运行时：skills 是什么**
- 引计算机领域名言，任何问题都能通过加一层抽象解决，除了抽象层过多本身；skills 本质上就是新加的一层抽象。
- 第一次学 skills 会自然联想到 LangGraph 等 agent 编排框架，主播判断这不是噱头，而是工程进化。
- skills 建立在 Claude Agent SDK（可理解为相当于 LangChain、LangGraph 的运行时）之上，先有给开发者的框架层，再封装成文档驱动的接口。
- skills 被定义为基于文档的 UI，门槛远低于用代码构建 agent。

**概念科普：Function Calling、MCP、Agent Skills 的关系**
- Function Calling 在最底层，给模型调用外部 API 的能力；MCP 是标准协议，把外部 API 暴露给模型去发现；skills 在最上层，主体是纯业务流程知识。
- skill 运行中仍通过 MCP 发现 API、再靠工具调用执行；skill 里还可以内嵌 MCP 与本地脚本，才构成完整定义。
- MCP 是 skill 的可选部分，skill 的本体是结构化、有 frontmatter 规范、有层级结构要求的超级 prompt。
- 用播客总结的例子说明：把音频转文字封装成 MCP 工具，总结逻辑写在 skill 里由自己模型执行。

**MCP 与 skill 的边界**
- 一个 MCP 可以直出从音频到总结的全过程，但那是把活外包给 API 背后的模型，是黑盒，里面可能也藏着 skill。
- skill 是让自家模型按可见的手册干活，过程透明；能做同一件事，概念与归属完全不同。

**回应不就是一堆 markdown 吗的吐槽**
- skills 有标准与规范：frontmatter 的 description 决定自动发现时能否匹配到正确的 skill。
- 通过自动发现、动态加载、渐进式加载子文档与脚本，缓解上下文压力，减少模型多轮执行后的遗忘与低质产出。
- 标准化与工具化是提高生产效率的必然方式，概念叫不叫 skills 不重要，能让人更少介入、让模型产出更高才算数。

**会做产品 vs 只会做技术**
- 能提出 skills、MCP 的团队是真会做产品，不只是解决技术问题；定义标准、命名概念本身是产品能力。
- Docker 对照：阿里早年在容器化和镜像上走得很深，却没想过把它标准化、抽象成可发布给全世界的产品。
- Anthropic 让用户只接触文档正是设计意图，文档驱动接口是给非开发者留的低代码入口。
- skills 开发被比作这个时代的低代码开发平台，配 web coding agent，简单工具一次成型概率很高。

**自家产品里的应用畅想**
- 产品哲学是极度简单、核心流程无人参与，所以主流程目前仍用 workflow 加 prompt，追求可控性与成本最优。
- 方向一：按播客品类挂不同领域背景的 skill，比如医疗类与 AI 科技类用不同的领域关键名词去总结。
- 方向二：把排障运维写成 skill，查日志、查数据库原数据、查代码分别封装成工具，出问题时让 agent 按流程自动排查，解放人力。
- 方向三：把发现某类节目总结质量差、拉数据、调 prompt、验证、回填这条人工调试链路也封装成 skill 自动化。

**skill 的粒度问题**
- skill 拆多大是艺术，没有标准答案，像微服务一样八个人有八种拆法。
- 参考判据：能叫出名字、新人要培训一下午、掌握后一句话就能触发，类似 Anthropic 官方内置的 PPT、Word、PDF skills。
- 主播倾向：大力度业务（如整个逐字稿结构化、翻译）值得做成 skill；个人运维类的大活也适合做成大 skill。
- 但产品主流程不要整个塞进一个 skill，保持 workflow 以保证稳定与成本，单节点的小活才适合 skill 化。

**workflow 与 agent 之争**
- workflow 是强规则运行，追求极致稳定；agent 是无规则运行，让模型自决策，智能上限更高并随模型升级抬升。
- skill 本身是以 agent 方式运行，就算在 skill 里写死规则做兜底，也不是 agent 驱动的主流方向。
- 显式点名 skill 或斜杠调用能显著提高命中率，服务两类场景：不知情终端用户靠 description 匹配，知情用户显式指定。

**模型能力是根因**
- 同样的 agent 配置，Gemini 2.0 与 3 Pro 的驱动体验差距巨大；Claude 与 MiniMax、智谱系模型在 coding 场景产出差异明显。
- 近一年模型优化方向已从文本质量、推理转向 agent 的规划推理执行链路，K2、DeepSeek V3.2 皆如此。
- 结论：agent 变好用主要是模型进步，skill 的最佳实践只是放大器，但并不能保证 workflow 级的确定执行。

**开源阳谋与生态之争**
- 阴谋论推演：skills 以 MIT 开源，社区贡献专业领域知识，模型厂可筛选内化到下一代产品与官方入口。
- 类比 Linux 内核与发行版、ChatGPT 推出健康版、OpenAI 花一亿美金收购四人六个月的健康 app 团队。
- 反方观点：skill 装的是持续迭代、带个性化的业务知识，不像常识能被吸收，更像可安装可替换的 app，会走向 marketplace。
- 收尾共识：无论如何，skills 加速了行业工程化进程，让未来的 AI 应用更规范、更高效，这就是好事。

## 思考

**别急着学新概念，先看清它替旧概念解决了什么**
任何新抽象出来时，老玩家都会本能地找反例。但对用 AI 干活的人来说，真正该问的不是它是不是又是一堆 markdown，而是它把我哪个手工动作变成了可复用资产。skills 把领域知识从 agent 的身体里拆出来，这是第一次让知识和执行器有了清晰的边界。该带走的方法：每当你被一个新概念砸中，先找它到底让谁少干了什么活，找得到就值得学，找不到再嘲讽不迟。

**判断一个活该不该自动化，看它的意外率，不看它的时髦度**
主播反复落到同一个决策轴上：确定性流程死守 workflow，高不确定性场景才放手给 agent。这其实是一套几乎所有人都能复用的分拣逻辑。大多数人栽跟头的地方，是把这个工具很火当成这个场景适合它。能带走一个判断：先给任务测意外率，能穷举步骤的走规则，穷举不了的再考虑放手给模型，顺序别反，钱和时间就都省下来了。

**agent 体验的差距，八分在模型，两分在你的调教**
这期最清醒的一句话藏在细节里：同样的写法，换一个模型就从驱动不动到顺滑。做 AI 应用的人太容易把功劳和锅都揽在自己身上，拼命调 prompt、拆 skill，却忘了底座模型每升一档，以前写的那些 workaround 可能全是负资产。真正省力的路径是先顶配模型验证可行，再向下兼容做减法，而不是在弱模型上堆技巧。体感不对时，第一个要换的是引擎，不是你的驾驶姿势。

**会做技术和会把技术变成标准，是两种天赋，前者廉价后者稀缺**
Docker 的故事扎在很多中国团队心上：技术早就跑在生产环境了，差的只是有人站出来说，这东西应该长成一个所有人都能用的样子。定义标准的人拿走生态，实现技术的人只拿到工时。对普通开发者，这不是劝你做大厂梦，而是提醒你把一成精力留给抽象这件事：把你做过的土办法，偶尔问一句它能不能被包装成别人也愿意直接用的东西。

**在 AI 生态里，你的专业知识是最硬的资产，也是最容易被惦记的资产**
开源阳谋那段推演之所以值得听，不是因为它多阴谋论，而是它逼每个人想清楚一个产权问题：你贡献出去的领域知识，到底是能被模型厂吸收的常识，还是带个人经验、会持续迭代的业务资产。前者随时可能被内化，后者才可能长成别人收不动的东西。能带走的判断：持续往自己的数据、方法论和不可复制的经验里投入，那才是别人既学不走、又愿意收购的部分。

**给 AI 的定义文档，本质上是在给未来的自己写岗位说明书**
description 决定命中率，粒度决定复用性，一句话触发加一下午培训是理想边界。这一整套其实都是人力资源管理的语言，因为你本质上是在训练一个能接活的实习生。想通这点，写 skill 就不再是技术活，而是管理活：你有多清楚一件事的边界，就能把多少自己从重复劳动里赎出来。普通人可以从今天最小的重复动作开始，写它的第一版说明文档。

**工具层解决怎么描述问题，不解决怎么保证结果，别把希望放错层**
节目最后给了一个很克制的结论：skills 让描述问题变简单，但效果仍要靠模型与调优。太多人把工具当灵药，换了个新抽象就以为效果会自己变好。真正稳定的杠杆永远是两条腿：选对足够强的模型，加上对自己业务判断力的打磨。工具会一年换一茬，这两条腿才是能跟着你走十年的东西。

**标准之争的赢家，从来不是发明者，是第一个让它被默认的人**
这期从头到尾其实在讲一件事：Anthropic 真正的护城河不是某个模型跑分，而是它每抛出一个抽象，全行业就默认跟进的能力。对个人也一样，你的影响力不取决于你多早做出某个东西，而取决于多少人愿意按你的命名和框架来组织自己的工作。所以别只顾低头干活，偶尔把你工作里的概念命名清楚、写清楚，这本身就是一种低成本的杠杆。
